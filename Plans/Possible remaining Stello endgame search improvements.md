# Possible remaining Stello endgame search improvements

**Verdict:** Phase 5 has a good chance of making Stello's exact solver faster. **Better move ordering at 11–13 empties has the strongest Stello evidence** for visiting fewer nodes. **Better preparation of the exact root has the greatest upside**, but its cost is uncertain: count every pre-search and every failed aspiration, not just the final proof. I would not yet predict that Phase 5 reaches **650M nodes** or beats both opponents at every thread count.

**Best additional experiment:** keep the proof already obtained **for each root move** across the win/loss/draw (WLD) and exact passes. It works with today's tables and can be tested before Phase 4. A small independent search checked the idea against exhaustive minimax; the result and its limits are below.

## Where the gap actually is

One thread, same FFO positions on the same machine. Each cell is **reported nodes / seconds for the whole set**. I checked the 80 one-thread results (four engines × 20 positions) against the [published per-move answers](../Stello.Net/tools/Stello.Benchmark/Data/ffo-40-59.txt): all were exact margins with optimal moves, including tied moves.

| Native Egaroucid | [512.6M / 9.470](benchmark-results/p0_egaroucid_cpp_ffo40-49_1t.json) | [15.54B / 325.701](benchmark-results/p0_egaroucid_cpp_ffo50-59_1t.json) |

- **Egaroucid really does report fewer nodes on all 20 positions**: Stello visits 2.09 times as many in aggregate on the first set and 1.96 times as many on the second. The plan's 2.21× is from an [earlier comparison](making-stello-5-0-findings.md#L285). Edax AVX, in contrast, visits **more** nodes than Stello 5.0 on eight of the 20; it still wins the harder set on time despite visiting substantially more nodes than Egaroucid. These are two different efficiency targets.
- **The gap is concentrated.** On 40–49, positions **48** (334.4M vs 77.9M) and **45** (300.3M vs 158.7M) account for **71.4%** of the 557.8M excess over Egaroucid. On 50–59, **53** (6.10B vs 1.16B) and **57** (5.33B vs 1.66B) account for **57.5%** of the excess. Position **59** looks spectacular (597.6M vs 8.8M, three winning `+64` moves), but accounts for only **3.9%** of that set's gap. Optimizing wipeouts alone cannot close it.
- **Use the current baseline for the gate.** [Phase 2](making-stello-6-0-findings.md#L315) still takes **1,070,469,669** nodes on 40–49, but only **14.1 s**. Getting below 650M requires cutting approximately **39.3%** of that tree. At 650M, beating Egaroucid's 9.470 s also requires about **68.6M nodes/s**; Stello's measured 76.04M leaves room for only about a **10% drop in throughput** from more expensive ordering. At eight threads Phase 2 already takes 2.591 s vs Egaroucid's 2.380 on 40–49, but 90.2 s vs 50.333 on 50–59. There is no matching 16-thread external result in the [Phase 0 comparison](making-stello-6-0-findings.md#L131).
- **A node is not a common unit.** Stello [counts each `ordering_value` call](../Stello.Cpp/src/endgame/search_impl.hpp#L597), even a static evaluation; Egaroucid's [depth-zero ordering case](../Egaroucid-main/src/engine/move_ordering.hpp#L236) evaluates the child directly without a search-node increment there. Its [solve runner](../Stello.Net/tools/Egaroucid.Runner/runner.cpp#L184) reports search plus clog nodes, and its [fixed-level driver](../Egaroucid-main/src/engine/ai.hpp#L208) accumulates pre-search work. Stello used hash bits 19, external engines 21; those settings do not mean equal allocated bytes. The wall-time gap survives these caveats. The totals alone do not tell us how much each pruning rule contributes.

## Assessment of the six Phase 5 proposals

The rankings are judgments about the [planned experiments](making-stello-6-0-plan.md#L308), not measured gains on the current engine. **NWS** is a null-window search: it asks which side of a threshold the score lies on. **PV** is the principal variation, the current best line. A **TT** is the transposition table that caches search results.

| Phase 5 proposal | Chance of a useful gain | How I would run it |
|---|---|---|
| **2. Order the 11–13-empty band better; shared/local TT boundary** | **High for fewer nodes; medium for wall time. Strongest evidence.** A [prior Stello trial](making-stello-5-0-findings.md#L412) cut 1t nodes **18.1%** but time only **9.6%** on 40–49. On 40–59/8t it cut nodes 16.3% but time only 5.2%; its 500 ms match scored 48.3%. | Hold table layout fixed; compare today's mobility, the cheap Edax-style key, then the incremental pattern key. A subset of the embedded evaluator need not rank moves as well as four patterns trained specifically for ordering. Measure first-move cutoffs and time by empties. **Then** move the TT boundary one ply at a time at equal total bytes. A 24 KiB local table may improve cache traffic but lose hits to collisions; do not credit its NPS gain to better pruning. |

That proves root order matters, not that more preparation always pays. | Compare, in order: better ordering seed with the present WLD driver; one selective pass with the same exact driver; then narrow aspiration vs WLD-first on the same seed and table. ### Fix the proposed parity rule before benchmarking it

With Stello's [exact null-window convention](../Stello.Cpp/src/endgame/search_impl.hpp#L139), the question is **`V > alpha`**. Terminal margins are even (empties go to the winner, draws score zero). The plan's literal `alpha += (alpha & 1)` changes the answer: with `alpha = 1` and true score `+2`, the original search must fail high; with `alpha = 2` it must fail low. For that predicate, canonicalize an **odd alpha down** to the preceding even integer, not up. Over all 65 even scores and 129 thresholds in `[-64,64]`, downward rounding preserved **all 8,385** comparisons; upward rounding changed **64**. Treat out-of-range sentinels explicitly and preserve valid fail-soft bounds and pass negation. This is not the same operation as [Edax widening an aspiration interval outwards](../edax-reversi-AVX-master/src/root.c#L482) or [Egaroucid adjusting a statistical ProbCut threshold](../Egaroucid-main/src/engine/multi_probcut.hpp#L97).

## Additional experiments not found as Stello trials

### 1. Carry certified bounds for each root move across proof passes

[Stello's driver](../Stello.Cpp/src/search/engine_impl.hpp#L254) uses a WLD result to set the next window (in fact it already uses the **fail-soft score**, not just the sign). [The root](../Stello.Cpp/src/search/engine_impl.hpp#L1329) retains improvements for move ordering but not a lower/upper proof interval per move. A child TT hit can recover some work, but that depends on residency and still requires entering the search. This proposal is **per move, for this root only**: neither a unified TT nor another aspiration policy.

Keep a lower and upper bound in exact disc units per legal root move. Update them from **completed nonselective** searches, using the window actually searched and the root player's perspective. Do not invent results for unsearched siblings after a winning cutoff. Skip a move if its upper bound cannot beat a witnessed incumbent; finish once a legal move's lower bound reaches the maximum remaining upper bound. Keep that witness, not a move known only by an upper bound. Preserve deterministic ties where required; a mode promising *all* optimal moves must still establish ties.

Two revealing cases: after **proving a loss**, the root value is at most `-2`; proving one move achieves at least `-2` finishes the margin (FFO **53** and **54**). At the other extreme, one move **proved** to achieve `+64` settles **59** immediately. The latter does not require a speculative wipeout search. A WLD win on its own does **not** prove `+64`. The same interval bookkeeping applies on aspiration retries, but never import a selective score as a bound. The [interruption regression](making-stello-3-1-findings.md#L74) is a necessary test: an unfinished pass is not automatically exact.

**Small falsification test, not a Stello benchmark:** I took the first 150 [random low-empty positions](../Stello.Net/tools/Stello.Benchmark/Data/endgame-random-low.txt) having 3–6 empties, in file order. A plain one-thread fail-soft alpha-beta reference used square order, a WLD pass, then the same sign-dependent exact window with the WLD move first. The trial changed only retention/use of root proof intervals; neither side had a subtree TT. Including both passes, recursive calls fell from **17,859 to 16,170 (9.46%)**: 64 roots cheaper, 86 equal, none more expensive. Exhaustive minimax verified the **score and returned move** for both on all 150. Real Stello has a TT, different ordering and specialized leaves: the percentage is **not** an FFO prediction. First count how many root calls the current TT already resolves cheaply.

### 2. Reuse the scout's stronger bound at the serial exact root

If a later root move's null-window probe returns a fail-soft lower bound `g` with `alpha < g < beta`, Stello's [serial root re-search](../Stello.Cpp/src/search/engine_impl.hpp#L1335) reopens the entire old `[-beta, -alpha]` child window. [Its own interior solver](../Stello.Cpp/src/endgame/search_impl.hpp#L296), [parallel endgame child](../Stello.Cpp/src/search/ybwc_impl.hpp#L103) and [Egaroucid's root](../Egaroucid-main/src/engine/midsearch.hpp#L602) already start that re-search at the stronger bound (`[-beta, -g]` from the child side). This is an independent, small experiment even without per-move storage. Restrict the first A/B to **exact** searches, keep the original lower-bound witness, and intersect with the new result: equality at `g` can complete a proof; a contradictory result is not a new exact value.

Count qualifying re-searches, `g - alpha` and their elapsed time. If nearly all improvements are a single score step, or TT narrowing already achieves the same effect, drop it. A related second test, **not bundled**: when a recursive PV call now receives a true unit window, dispatch it to NWS instead of continuing the wide-window first-child path. Compare [Stello's entry dispatcher](../Stello.Cpp/src/endgame/search_impl.hpp#L125) with [Egaroucid's recursive dispatcher](../Egaroucid-main/src/engine/midsearch.hpp#L160). Preserve pass state, score perspective and valid TT bounds. Neither change is a new pruning assumption.

### 3. Use a different handoff depth for selective preparation than for exact proof

This is a concrete opponent difference that the Phase 5 proposal to **add passes** does not specify. [Egaroucid's dispatcher](../Egaroucid-main/src/engine/midsearch_nws.hpp#L337) hands NWS to its specialized exact tail at **13 empties** for 100%, but only **9 empties** for a selective search. Thus at 10–13 empties the selective pre-search can still use its ordinary TT, move ordering and MPC. [Stello's limits](../Stello.Cpp/src/search/engine.hpp#L34) hand off at 13 regardless of stage, and [endgame ProbCut](../Stello.Cpp/src/endgame/search_impl.hpp#L372) starts at 16. This can change the cost **and quality** of the seed for a later proof. It is not a speedup to the present cold `Solve` path, which skips selective passes.

After testing one warm pass, hold its stage schedule fixed. First lower only the *internal* selective verification floor to 14; next try retaining the selective dispatcher to 11 or 9, keeping the 100% tail untouched. Keep the root eligibility threshold unchanged. Measure pre-search cost **plus** final proof cost, seed error vs exact margin, and move rank. Calibrate the short probes on held-out exact positions. In particular, do not put selectively pruned bounds in Stello's [untagged local exact table](../Stello.Cpp/src/endgame/local.hpp#L9); only use it for subtrees known to be nonselective. The [old 14-empty end-MPC experiment](improve-stello-strength-findings.md#L394) tested a timed pass and root handover, not this stage-specific 10–13 split.

I would **not** list connected-region parity, unseeded MTD(f), general root clog search or a larger hash as new. The [early solver notebook](Stello%20porting%20documentation.md#L679) and [5.0 clog trial](making-stello-5-0-findings.md#L396) already cover them. Also, Egaroucid's optional *interior* aspiration code is [disabled by default](../Egaroucid-main/src/engine/setting.hpp#L150); it is not evidence for the measured gap.

## Decision order

1. **Instrument proof work before changing it.** One thread, fresh table per root, both FFO sets. Separate warm-up, WLD, exact first child, root scouts/re-searches and aspiration retries. Count main-tree nodes, ordering visits, TT cutoffs, stability cutoffs and leaves by empties. Report whole-solve elapsed time as well as nodes; retain the existing node definition. Use positions 45/48/53/57 for diagnosis, **not** as the acceptance suite.
2. **Run isolated trials:** per-root proof reuse; the serial scout bound; cheap 11–13 ordering vs incremental ordering; then one warm pass vs the current WLD-first driver. Test stage-dependent handoff only if warm preparation helps. Remeasure the combined winner: the same subtree cannot be saved twice. Prove every FFO root margin **and an optimal move**; also use [random endgames](../Stello.Net/tools/Stello.Benchmark/Data/endgame-random.txt), [pass-heavy positions](../Stello.Net/tools/Stello.Benchmark/Data/endgame-random-pass.txt), early double-pass ties/losses, score extrema, interrupted passes and restricted root moves.
3. **Only then test parallel and playing results.** Repeat at 8 and 16 threads, record median whole-pass wall time and node inflation, and get matching 16t external numbers before claiming superiority. For timed play record first **proven** solve and disc loss separately from selective terminal depth; follow the [500 ms / 2 s paired gates](making-stello-6-0-plan.md#L35). An exact analysis speedup, an earlier proof in a game and an Elo gain are three different results. No production engine changes, FFO reruns or matches were made for this report.
